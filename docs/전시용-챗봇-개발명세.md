# 졸업전시용 이미지 챗봇 — 개발 명세

이 문서는 Claude Code에 그대로 전달하기 위한 명세입니다.
아래 내용을 기반으로 개발을 진행해 주세요.

---

## 1. 무엇을 만드는가

졸업전시 부스에 설치할 **AI 챗봇 웹앱**입니다.

관람객이 자기 핸드폰에 저장해둔 추억 사진을 올리면, 부스에 놓인 맥북 화면에서 그 사진을 가지고 챗봇과 대화합니다.

**사용자 흐름**

1. 관람객이 부스 앞에 선다. 맥북 화면에 챗봇 UI와 QR 코드가 떠 있다.
2. 관람객이 자기 폰으로 QR을 찍는다.
3. 폰 브라우저에 **업로드 전용 페이지**가 열린다 (버튼 하나뿐인 아주 단순한 화면).
4. 앨범에서 추억 사진을 고르고 전송한다.
5. **맥북 화면의 채팅창에 그 사진이 자동으로 나타난다.**
6. 이후 대화는 전부 맥북에서 진행한다. 폰은 더 이상 쓰지 않는다.

**핵심 포인트**: 폰은 "사진 전송 창구" 역할만 합니다. 챗봇 인터페이스는 맥북입니다.

---

## 2. 왜 이 구조인가 (설계 배경)

개발할 때 이 이유들을 염두에 두면 판단이 쉬워집니다.

- **왜 폰에서 대화하지 않는가**: 전시 기획상 관람객이 부스 앞 큰 화면에서 경험하는 것이 의도. 폰은 사진 소스일 뿐.
- **왜 맥북에 파일 선택창을 두지 않는가**: `<input type="file">`을 클릭하면 macOS Finder가 열리면서 **개발자 본인의 바탕화면과 개인 파일이 관람객에게 그대로 노출됨**. 전시 부스에서는 치명적. 그래서 맥북 UI에는 파일 선택 기능을 아예 넣지 않는다.
- **왜 클라우드 배포가 아닌가**: 코드가 맥북에 있어야 현장에서 즉시 수정 가능. 또 관람객 사진이 외부 서버에 남지 않아 개인정보 측면에서 안전.
- **왜 터널을 쓰는가**: 아래 3번 참고.

## 3. 네트워크 구성 — Cloudflare Tunnel

### 문제

맥북에서 서버를 띄우면 주소는 `http://localhost:8000` 또는 `http://192.168.x.x:8000`입니다. 이건 같은 네트워크 안에서만 통하는 주소라 관람객 폰(LTE)에서는 접속이 안 됩니다.

전시장 공용 Wi-Fi에 다 같이 붙는 방법도 있지만, **공용 Wi-Fi는 AP isolation(클라이언트 격리)이 걸려 있는 경우가 매우 많아** 폰 → 맥북 접속이 차단됩니다. 당일에 발견하면 대응이 불가능합니다.

### 해결

**Cloudflare Tunnel**로 맥북 로컬 서버에 공개 HTTPS 주소를 붙입니다.

```bash
brew install cloudflared
cloudflared tunnel --url http://localhost:8000
```

실행하면 `https://xxxx-yyyy-zzzz.trycloudflare.com` 형태의 주소가 터미널에 출력됩니다. 계정 가입 불필요, 무료.

```
관람객 폰 (LTE)
    ↓  https://xxxx.trycloudflare.com
Cloudflare
    ↓  터널
맥북 localhost:8000
```

### 이 방식의 이점

- 전시장 Wi-Fi에 전혀 의존하지 않음 (관람객은 각자 데이터 사용)
- **HTTPS가 자동 적용됨** — 모바일 브라우저가 HTTP 사이트의 파일 업로드에 경고를 띄우거나 차단하는 문제를 회피
- 포트포워딩·방화벽 설정 불필요

### 주의사항 (중요)

- 터널 프로세스를 종료하면 주소가 죽는다.
- **재시작할 때마다 주소가 바뀐다.**
- 따라서 **QR 코드를 종이에 인쇄해두면 안 된다.** 서버가 현재 터널 주소를 알아내서 화면에 QR을 동적으로 렌더링해야 한다.
- 구현 방법: 환경변수 `PUBLIC_BASE_URL`로 터널 주소를 주입받게 하고, 실행 스크립트에서 `cloudflared` 출력을 파싱해 자동으로 넣어주면 편하다. 최소한 수동 입력이라도 가능해야 한다.

> ngrok도 같은 일을 하지만 무료 플랜은 접속자에게 경고 페이지를 한 번 띄웁니다. 관람객이 헷갈릴 수 있어 Cloudflare를 권장합니다.

## 4. 기술 스택

특별한 제약은 없으나 아래 조합을 권장합니다. 익숙한 스택이 있으면 바꿔도 무방합니다.

- **백엔드**: Python + FastAPI (또는 Node.js + Express)
- **프론트엔드**: 별도 프레임워크 없이 정적 HTML/CSS/JS로 충분. 화면이 2개뿐이고 상태도 단순함.
- **AI 모델**: 이미지 입력을 지원하는 API (Claude, GPT 등). **로컬 모델은 권장하지 않음** — GPU 없는 맥북에서 이미지 추론은 너무 느려 관람객이 이탈함.
- **DB**: 불필요. 세션은 메모리 내 dict로 관리.

## 5. 구현할 엔드포인트

| 메서드 | 경로 | 용도 |
|---|---|---|
| GET | `/` | 맥북용 챗봇 화면. 세션 생성 + QR 표시 |
| GET | `/u/{sid}` | 폰용 업로드 페이지 |
| POST | `/u/{sid}` | 이미지 수신 |
| GET | `/events/{sid}` | 맥북이 새 이미지 도착을 감지 (SSE 권장, 1초 폴링도 무방) |
| POST | `/chat/{sid}` | 채팅 메시지 → AI API 호출 → 응답 반환 |
| POST | `/reset` | 세션 초기화 (새 관람객용) |

### 세션 관리

- 세션 ID는 랜덤 문자열 (예: 8자리)
- 서버 메모리에 `{sid: {images: [...], messages: [...], last_active: timestamp}}` 형태로 보관
- DB나 파일 저장 불필요

## 6. 폰 업로드 페이지 상세

### HTML

```html
<input type="file" accept="image/*" multiple>
```

- **`capture` 속성을 넣지 말 것.** `capture`가 있으면 카메라가 바로 켜진다. 이 기획은 **앨범에 저장된 사진**을 고르는 것이므로 반드시 빼야 한다.
- `multiple`은 넣어둔다. 관람객이 여러 장 올리고 싶어할 가능성이 높다.

### 클라이언트 측 리사이즈 (필수)

추억 사진은 원본 크기라 보통 4~8MB입니다. 전시장 LTE로 그대로 올리면 10초 이상 걸려 관람객이 "안 되나?" 하고 떠납니다.

- canvas로 **긴 변 1568px, JPEG quality 0.8** 로 축소 후 전송
- 결과물은 300KB 안팎, 화질은 충분
- 토큰 비용도 함께 절감됨

### EXIF 회전 처리 (필수)

아이폰 세로 사진을 canvas에 그리면 **옆으로 눕는 현상**이 발생합니다. EXIF orientation을 읽어 보정하거나, `createImageBitmap(file, { imageOrientation: 'from-image' })`를 사용하세요. 누운 사진이 그대로 모델에 들어가면 엉뚱한 답이 나옵니다.

### HEIC 대응 (필수)

아이폰 기본 촬영 포맷은 HEIC입니다. 브라우저 canvas를 거치면 JPEG로 변환되므로 클라이언트 리사이즈를 구현하면 대부분 해결되지만, **폴백 경로에서 원본이 그대로 전송될 경우** 서버에서 열지 못합니다.

- Python이면 `pillow-heif` 설치
- 또는 서버가 HEIC를 받으면 명확한 에러 메시지를 반환

**반드시 실제 아이폰으로 테스트할 것.** 당일에 발견하면 늦습니다.

### UI 요구사항

- 버튼 하나. 설명 없이도 뭘 해야 하는지 알 수 있어야 함
- **업로드 진행률 표시** (없으면 멈춘 줄 알고 재시도함)
- 전송 완료 시 "맥북 화면을 봐주세요" 안내
- 하단에 개인정보 안내 문구 (9번 참고)

## 7. 맥북 챗봇 화면 상세

- 화면 한쪽에 QR 코드 상시 표시 (충분히 크게)
- 사진이 도착하면 채팅창에 자동 삽입 + 시각적 피드백 (애니메이션이나 사운드)
- 대기 시간 연출 필요 — 이미지 추론은 수 초 걸림. 로딩 인디케이터가 없으면 관람객이 화면을 떠남
- 텍스트는 멀리서도 읽히는 크기로
- **세션 리셋 버튼을 크고 명확하게 배치**

### 세션 전환 처리 (실제로 가장 자주 터지는 부분)

관람객 A가 사진을 올리고 대화한 뒤, 관람객 B가 새 사진을 올리면 **A의 대화 맥락이 남아 있어 엉뚱한 답변이 나옵니다.**

- 리셋 시 대화 기록 + 이전 이미지를 **함께** 비울 것
- 리셋하면 새 세션 ID를 발급하고 QR도 갱신
- **3분간 입력이 없으면 자동 리셋** (운영자가 매번 누르지 않아도 되게)

## 8. 보안

- **API 키는 절대 프론트엔드에 두지 말 것.** 공개 URL이므로 즉시 유출됨. 반드시 서버 환경변수(`.env`)로만 관리하고, 모든 AI 호출은 서버를 경유.
- `.gitignore`에 `.env` 포함
- 업로드 엔드포인트에 파일 크기 상한 (예: 10MB) 및 MIME 타입 검증
- 세션 ID를 모르면 업로드 불가하도록

---

## 9. 개인정보 처리

추억 사진에는 가족·친구의 얼굴이 거의 확실히 포함됩니다. 이건 개인정보이므로 신경 써야 하고, 졸업전시 심사에서 질문이 나올 수 있는 부분이기도 합니다.

- **디스크에 저장하지 말 것.** 메모리에만 보관하다가 세션 종료 시 폐기하는 구조로. 파일이 남지 않으면 관리할 것도 없어집니다.
- 폰 업로드 페이지 하단에 명시: *"업로드한 사진은 대화가 끝나면 즉시 삭제되며 저장되지 않습니다."*
- 부스에도 같은 내용을 안내물로 부착

## 10. 데모 모드 (반드시 구현)

전시장 네트워크 장애, API 장애, 요금 한도 초과 등으로 시연이 불가능해지는 상황은 생각보다 자주 발생합니다.

- 미리 준비한 샘플 사진 몇 장 + 그에 대한 응답을 하드코딩
- **키보드 단축키 하나로 전환** 가능하게
- 최악의 경우에도 관람객과 심사위원에게 보여줄 것이 남습니다

## 12. 개발 순서 제안

1. 로컬에서 서버 + 두 페이지 골격 (QR, 업로드, 폴링) — 사진이 맥북 화면에 뜨는 것까지
2. Cloudflare Tunnel 연결해서 실제 폰으로 업로드 테스트
3. 클라이언트 리사이즈 + EXIF + HEIC 대응
4. AI API 연동 및 대화 기능
5. 세션 리셋 / 자동 타임아웃
6. UI 다듬기 (전시용 크기·연출)
7. 데모 모드
8. 실기기 리허설

1~2단계에서 실기기 테스트를 먼저 통과시키는 게 중요합니다. 여기서 막히면 나머지가 다 무의미해집니다.

---

## 13. 아직 정해지지 않은 것

기획자에게 확인 후 반영이 필요한 항목입니다.

- 챗봇이 사진으로 **무엇을 하는지** (스토리 생성 / 분석 / 회상 대화 등) — 시스템 프롬프트 설계에 직결
- 대화 길이 (한두 번 주고받고 끝인지, 계속 이어지는지) — 세션 타임아웃 시간에 영향
- 결과물을 관람객이 가져갈 수 있어야 하는지 (있다면 결과 저장·전송 기능 추가 필요)

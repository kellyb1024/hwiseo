# Teams UI Kit에서 뽑은 것 (진행 중)

출처: Microsoft Teams UI Kit v5.0 (Community), Fluent 2 기반. 2026-08-26 플러그인으로 직접 추출.

## 1. 보라 팔레트 — 실제 값

| 역할 | HEX | 어디에 쓰였나 |
| :-- | :-- | :-- |
| Primary (brand) | `#5b5fc7` | Accent 버튼 배경, 활성 상태, 선택된 항목 |
| Primary hover/pressed | `#4f52b2` | 같은 버튼의 눌린 상태 |
| Primary 밝은 쪽 | `#7f85f5` | 다크 모드에서의 같은 역할 |
| 테두리용 연보라 | `#8b8cc7` | outline 버튼 테두리 |
| 어두운 보라 | `#464775` / `#444791` | 다크 표면 |

**핵심 관찰 — 보라가 나온 횟수:** Button 프레임 전체에서 흰색 195회 vs 보라 22회.
즉 **화면의 90% 이상이 무채색이고 보라는 "지금 누를 것" 하나에만** 쓰인다.
연보라를 배경이나 장식으로 깔지 않는다. 이게 우리가 따올 규칙.

## 2. 버튼 3종 위계

- **NEUTRAL** (기본) — 흰 배경 + 회색 테두리. 대부분의 버튼
- **ACCENT** — 보라 배경 + 흰 글씨. **화면당 하나**
- **OUTLINE** — 투명 배경 + 연보라 테두리 `#8b8cc7`

## 3. 모서리 반경

`4px`가 압도적(58회). `2px` 소수, `22/100px`는 알약형(아바타·상태 배지)뿐.
→ 카드·입력창·버튼 전부 **4px**. 우리 스펙의 "둥근 모서리 최소화"와 맞는다.

## 4. 타입 스케일 (Segoe UI)

| 용도 | 크기/행간 | 굵기 |
| :-- | :-- | :-- |
| 본문·입력 | 14 / 20 | 400 |
| 버튼 라벨 | 14 / 19 | 600 |
| 보조 텍스트 | 12 / 16 | 400 |
| 섹션 라벨 (대문자) | 11 / 32 | 600 |
| 제목 | 24 / 32 | 700 |

→ **본문 14, 버튼 14, 보조 12, 라벨 11.** 크기가 네 개뿐이다.
(단 전시는 멀리서 읽어야 하므로 우리는 이 비율만 쓰고 절대값은 키운다)

## 5. 입력창 구조

States(Rest / Focus / Focus-텍스트 입력됨 / Keyboard focus) + Types(Prefix, 에러) 로 나뉨.
에러는 팝업이 아니라 **입력창 바로 아래 인라인 텍스트**("Invalid email format.").
→ 우리도 토스트 쓰지 말고 인라인.

## 6. Layout & Scaling 페이지 (zip으로 확인)

- **4px 배수 그리드.** 간격 단위 4·8·12·16·20·24·28
- 버튼 내부 여백 12px / 아이콘-글자 간격 8px
- **1920×1080·100%에서 전부 보일 것. 200% 확대에서 잘리지 말 것** → 전시 맥북 기준으로 그대로 채택
- 대비는 WebAIM으로 검사할 것

# Bots 페이지 (2026-08-26 추출)

## 7. ★ 연보라의 진짜 용법 — 말풍선 배경으로 "누구 말인지"를 표시

`Chatting with a bot` 프레임의 색 사용 실측:

| 색 | 횟수 | 실제 노드 | 의미 |
| :-- | --: | :-- | :-- |
| `#ffffff` | 660 | 봇/상대방 말풍선, 배경 | 상대의 말 |
| `#e8ebfa` | 22 | `Thread/MessageBG/ChatMyMessage` | **내가 한 말** |
| `#5b5fc7` | 28 | `Selected-bar` (2×48px), 활성 아이콘, 배지 | 지금 선택된 것 |

**규칙 세 줄:**
1. **아주 옅은 연보라 `#e8ebfa`가 "내 말"의 배경.** 진한 보라가 아니다
2. **진한 보라 `#5b5fc7`는 2px 막대와 배지 같은 극소 면적에만.** 큰 면에 절대 안 칠한다
3. 상대(봇)의 말은 **색이 없다.** 흰 바탕 위 검은 글씨

### 휘서에 어떻게 뒤집어 쓰는가
Teams는 연보라 = 사람. 우리는 연보라 = 기계, 앰버 = 사람으로 **정반대**다.
따라서 색을 베끼지 말고 **구조만** 가져온다:

- 목소리 구분은 **면(배경 틴트)** 으로 한다. 글자색만 바꾸지 않는다
- 틴트는 **거의 안 보일 만큼 옅게**. 어둠 `#100D16` 위라면 연보라 5~8% 정도
- **채도 높은 색은 극소 면적에만** — 턴 표시 점, 얇은 선, 커서. 우리 `lantern`/`B3A5DC` 원색을 넓게 칠하지 않는다
- 사람의 답변 자리에 앰버 틴트를 아주 옅게 → 3턴 진행될수록 화면에 앰버 면이 늘어난다. **색 규칙이 저절로 증명된다**

## 8. 봇 화법 가이드 — 프롬프트에 직접 반영할 것

Microsoft가 명시한 Do / Don't:

- **Do: Establish a clear persona** — 톤을 문서로 정해두라 (친근/사실만/괴짜). → 우리 `ask.v1.md`의 톤 규칙이 이것
- **Do: Clearly convey what your bot can do** — 첫 인사에서 할 수 있는 일을 말한다
- **Don't: Obscure your bot's features** — 정체불명 인사는 의심을 산다
- **Do: Recognize non-questions** — "안녕", "고마워", 오타에도 반응할 것
- **Don't: Miss out on opportunities to delight** — 단순한 말에 어색하게 답하지 말 것
- **Do: Provide help** — 못 할 때 빠져나갈 길을 준다 (우리 `SkipControl`)
- **Don't: Leave users stranded** — 막히면 즉시 이탈한다
- **Do: Allow people to see sensitive information only in a personal context** — 민감한 내용은 사적인 자리로. → **공개 부스에서 옛 기억을 말하게 하는 우리 설계에 정확히 해당.** 칸막이·헤드폰이 이 원칙의 물리적 구현

### ⚠️ 우리와 충돌하는 항목 하나
> **Don't: Make multi-turn interactions tedious** — 한 가지 일을 끝내려고 대화를 길게 끄는 것은 느리고 복잡하다

Teams 기준으론 다턴 대화가 안티패턴이다. 하지만 우리는 **대화 자체가 목적**이지 작업 완료 수단이 아니다.
다만 이 경고가 유효한 지점이 있다 — **질문이 정보 수집으로 느껴지면 즉시 지루해진다.**
→ 3턴 제한이 이 문제의 답이고, 질문은 "채널만 열고 내용은 제안하지 않는다" 규칙을 지켜야 한다.

## 9. 봇 첫인사 구조 (Bot introductions)

> "It's critical that your bot introduces itself and describes what it can do. This initial exchange helps people ... get comfortable interacting with it."

구성: **인사 + 무엇을 할 수 있는지 + 어떻게 말 걸면 되는지 예시.**
→ 우리 B0 대기화면 / B1 소환화면이 이 역할. "사진 한 장을 올려주세요"만으로는 부족하고,
휘서가 무엇을 하는 존재인지 한 줄이 필요하다.

## 11. 라이트/다크에서 같은 램프를 어떻게 뒤집어 쓰는가 ★★

같은 5색을 테마별로 **역할만 바꿔서** 재사용한다. 새 색을 만들지 않는다.

| 자리 | 라이트 테마 | 다크 테마 |
| :-- | :-- | :-- |
| 1 | `#E8EBFA` = **BG 1** (배경) | `#7F85F5` = **FG 1** (글자) |
| 2 | `#9299F7` = **BRD 1** (테두리) | `#444791` = **BRD 1** (테두리) |
| 3 | `#5B5FC7` = **FG** (글자·주요버튼) | `#3D3E78` = **BG 2** (배경) |
| 4 | `#4F52B2` = **FG 2** | `#2F2F4A` = **BG 1** (배경) |

**핵심:** 라이트에서 배경이던 가장 연한 색이, 다크에서는 **글자색**이 된다.
어두운 바탕에서는 **연한 보라를 글자에 쓰고, 배경은 아주 어두운 보라**(`#2F2F4A`, `#3D3E78`)를 쓴다.

### → 휘서에 바로 적용 (우리는 다크 온리)
우리 배경은 `#100D16`이므로 **다크 테마 열만 보면 된다.**

| 역할 | Teams 다크 | 휘서 대응 |
| :-- | :-- | :-- |
| 기계 목소리 글자 | `#7F85F5` (FG 1) | `#B3A5DC` — 이미 우리 값이 이 자리에 정확히 맞다 |
| 기계 쪽 면/틴트 배경 | `#2F2F4A`, `#3D3E78` (BG 1·2) | **우리한테 없던 값.** `#100D16`과 `#B3A5DC` 사이의 어두운 보라를 새로 정해야 한다 |
| 얇은 테두리 | `#444791` (BRD 1) | 질문 영역 경계선, 입력 커서 |

**즉 우리에게 부족했던 것은 "어두운 보라 면" 두 단계다.**
지금 우리 팔레트는 어둠(`#100D16`)과 밝은 연보라(`#B3A5DC`)뿐이라 그 사이가 비어 있다.
말풍선 틴트·선택 상태를 표현할 중간 단계가 없으면 결국 원색을 넓게 칠하게 되고, 그게 촌스러워지는 원인이다.

**제안 (앰버도 같은 구조로):**

```
기계(연보라)                          사람(앰버)
purple-fg    #B3A5DC  글자·질문        amber-fg   #E9A24A  글자·이야기
purple-brd   #6E63A0  얇은 테두리       amber-brd  #8A5F28  얇은 테두리
purple-bg2   #2A2440  면 (진한 쪽)      amber-bg2  #3A2A18  면 (진한 쪽)
purple-bg1   #1A1626  면 (연한 쪽)      amber-bg1  #241B10  면 (연한 쪽)
어둠         #100D16
```
※ 위 6개 중간값은 Teams 램프의 명도 간격을 우리 색상환에 옮긴 초안. 실제 화면에서 눈으로 확정할 것.

# Type 페이지 (2026-08-26 추출)

## 14. 타입 스케일 — 7단계, 그게 전부다

> "Teams uses seven styles that range from level-one titles to captions."

| 스타일 | 크기/행간 | 명시된 용도 |
| :-- | :-- | :-- |
| Title 1 | **32 / 40** | **Greeting title** (인사 제목) |
| Title 2 | 28 / 36 | Page title |
| Title 3 | 24 / 32 | Email header |
| Headline | 20 / 28 | Page/pane header |
| Subheadline 1 | 18 / 24 | Subject title |
| **Body 1** | **14 / 20** | **Body / button** |
| Caption | 12 / 16 | Caption |

**행간 규칙:** 전부 4의 배수(40·36·32·28·24·20·16). 크기가 커질수록 행간 배율은 줄어든다
(32→1.25배, 14→1.43배, 12→1.33배). 큰 글씨는 좁게, 작은 글씨는 넓게.

**비율:** 32 / 28 / 24 / 20 / 18 / 14 / 12 — 위쪽은 4씩, 아래쪽은 2씩 좁아진다.

### → 휘서 적용
⚠️ **정정 (2026-08-26):** 전시 화면은 멀리서 읽는 것이 아니다. 관람객은 맥북 바로 앞에 서서
코앞에서 읽는다. **일반 웹 채팅(ChatGPT · Gemini · Claude) 과 같은 크기**로 간다.
크게 만들어야 하는 것은 화면이 아니라 **부스 사인물·안내판**이다.

7단계 구조와 4배수 행간 규칙만 가져오고, 절대값은 웹 채팅 표준을 따른다.

| 역할 | 휘서 크기/행간 | 비고 |
| :-- | :-- | :-- |
| 질문 (화면의 주인공) | 28 / 40 | 본문보다 확실히 크되 과하지 않게 |
| 이야기 본문 (명조) | 20 / 32 | 한글 명조는 행간을 넉넉히 |
| 확인 문장 | 18 / 28 | |
| 입력·답변 | 16 / 24 | GPT·Claude 본문과 같은 크기 |
| 안내·보조 | 14 / 20 | |
| 라벨 (턴 표시·연도) | 12 / 16 | |

→ **6단계.** 행간 전부 4배수 유지.

## 15. ★ 굵기 규칙 — 이 문장이 제일 중요하다

> **"Font weights are for identifying specific elements and conveying states.
> Don't use bold to create hierarchy in your text.
> Instead, use a different shade of grey and the SemiBold weight."**

**굵기로 위계를 만들지 말 것. 대신 회색 명도를 바꾸고 SemiBold를 쓸 것.**

| 굵기 | 명시된 용도 |
| :-- | :-- |
| Regular | 본문 |
| *Italic* | **임시 상태** (temporary states) |
| SemiBold | 소제목 |
| Bold | **읽지 않은 활동** (unread activity) |

굵기가 장식이 아니라 **상태를 뜻하는 신호**로 배정돼 있다. Bold는 "안 읽음"이라는 뜻이지 "중요함"이 아니다.

### → 휘서 적용
- 위계는 **크기 + 명도**로. 굵기로 만들지 않는다
- 우리 화면에서 굵기에 의미를 배정한다면: **Regular = 확정된 말**, **Italic = 아직 진행 중인 상태**
  (예: 휘서가 생각 중일 때, 사용자가 입력 중일 때)
- 명조/고딕의 구분이 이미 "사람 말 / 기계 말"을 하고 있으므로, **굵기까지 의미를 주면 과하다.**
  → 굵기는 Regular 하나로 통일하고, 필요하면 SemiBold 하나만 추가

## 16. 플랫폼별 서체

- 웹·데스크톱: Segoe UI / 안드로이드: Roboto / iOS: SF Pro
- → 각 플랫폼의 시스템 서체를 따른다. **우리는 웹 하나이므로 Pretendard로 통일하면 된다.**
